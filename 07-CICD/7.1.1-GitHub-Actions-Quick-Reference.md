# GitHub Actions CI/CD — Quick Reference & Mnemonics

## The scaffold — say this before writing any workflow

**Top level: "NOJ"** → Name → On → Jobs **Inside a job: "RNS"** → Runs-on → Needs → Steps **Inside a step: "NUW" or "NRE"** → Name+Uses+With (pre-built action) OR Name+Run+Env (raw shell)

**Full chant: "NOJ, RNS, NUW or NRE"**

## The skeleton

```yaml
name: <workflow name>
on:
  push:
    branches: [main]

jobs:
  job-name:
    runs-on: ubuntu-latest
    needs: other-job              # optional — controls ORDER only
    if: github.event_name == 'push'   # optional — controls WHICH TRIGGER runs this job
    steps:
      - name: Action-based step
        uses: actions/checkout@v6
        with:
          token: ${{ secrets.X }}

      - name: Shell-based step
        run: pytest -v
        env:
          MONGO_URI: ${{ secrets.MONGO_URI }}
```

## Standard 3-stage pattern (test → build-and-push → deploy)

```yaml
name: CI-CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: '3.11'
      - run: pip install -r requirements.txt
      - run: pytest -v

  build-and-push:
    runs-on: ubuntu-latest
    needs: test
    if: github.event_name == 'push'    # CRITICAL — see Rule 1 below
    steps:
      - uses: actions/checkout@v6
      - uses: docker/login-action@v4
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: user/app:${{ github.sha }}

  deploy:
    runs-on: ubuntu-latest
    needs: build-and-push
    steps:
      - uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ubuntu
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |
            echo "MONGO_URI=${{ secrets.MONGO_URI }}" > /home/ubuntu/.env.app
            chmod 600 /home/ubuntu/.env.app
            docker pull user/app:latest
            docker stop app || true
            docker rm app || true
            docker run -d --name app -p 80:5000 --env-file /home/ubuntu/.env.app user/app:latest
```

## Four rules — each one is a real bug hit and fixed this cycle, not theory

### Rule 1: `needs:` controls order, NOT which trigger runs a job

**Real bug (taskmanager project):** `build-and-push` only had `needs: test`. Since the whole workflow's `on:` block included `pull_request`, opening a PR ran the _entire_ pipeline — including pushing an unreviewed image to Docker Hub as `:latest`.

**Fix:** add `if: github.event_name == 'push'` to any job that should only run on real merges, not PRs.

### Rule 2: secrets can be valid but still wrong — check the scope, not just existence

**Real bug (taskmanager, then flask-mongo-app):** first error was `incorrect username or password` (token genuinely invalid/expired). Regenerated it — new error: `insufficient scopes` (token was valid but created as Read-only instead of Read & Write).

**Lesson:** "unauthorized" from a registry can mean two different things — invalid credential vs. valid-but-under-permissioned credential. Same error class, different root cause, different fix.

### Rule 3: action versions go stale, and GitHub actually retires old runtimes on real deadlines

**Real event, not hypothetical:** GitHub retired Node.js 20 as an Actions runtime with a **September 16, 2026** deadline — hit almost exactly on that date while reviewing `taskmanager`'s pipeline. Old actions (`checkout@v3`, `setup-python@v4`) risked breaking outright, not just showing warnings.

**Habit:** periodically check current major versions of `checkout`, `setup-python`, `login-action`, `build-push-action` — don't trust a version pinned months/years ago.

### Rule 4: a `test` job should always gate `build`/`deploy` via `needs:`

**Real gap found (flask-mongo-app):** the original pipeline had zero tests — straight from checkout to build-and-push to a live EC2 deploy. A broken app would have shipped to production on the very next push.

**Fix:** add a `test` stage first; every downstream job chains `needs:` back to it.

## The secrets-hygiene lesson — worth its own section, recurring across every project this cycle

**A secret being "in GitHub Secrets" only protects it up to the point it's injected somewhere.** What happens _after_ injection matters just as much.

**Real bug (flask-mongo-app):**

```yaml
# WRONG — visible in plaintext to any process on the server via `ps aux`
docker run -e MONGO_URI="${{ secrets.MONGO_URI }}" ...
```

```yaml
# FIXED — written to a permission-restricted file, referenced via --env-file
script: |
  echo "MONGO_URI=${{ secrets.MONGO_URI }}" > /home/ubuntu/.env.app
  chmod 600 /home/ubuntu/.env.app
  docker run --env-file /home/ubuntu/.env.app ...
```

**One-liner for interviews:** _"A credential being 'in a secret' from GitHub's perspective and being 'actually protected at every hop' are two different questions — I found a case where the secret was safe in GitHub but ended up plaintext-visible in a running process's argument list the moment it reached the server."_

## Small things worth remembering, each from a real moment

- **`npm ci`, not `npm install`, in any pipeline** — `ci` fails loudly on lockfile mismatch instead of silently reconciling it; reproducibility matters more in CI than convenience
- **`${{ github.sha }}` (or `${{ github.run_number }}`) as an image tag, not `:latest`** — every deployed image traces back to the exact commit/run that produced it
- **A workflow with no `credentialsId`/no login step for `git checkout` is fine — for public repos only.** Private repos need the credential; public ones don't (this isn't a security gap, it's a correct difference based on visibility)
- **Pipeline scripts assuming pre-existing server setup (a running PM2 process under a specific name, Docker already installed) are fragile if that setup isn't documented anywhere in the repo itself** — someone else picking up the project has no way to know these prerequisites exist

### Explaining the pipeline itself, simply

_"I built a CI/CD pipeline using GitHub Actions that has three stages, running one after another._

_First stage is **test** — it checks out my code, installs the Python dependencies, and runs my test suite. If any test fails, the pipeline stops right there — nothing gets built or deployed._

_Second stage is **build and push** — this only runs if tests passed. It builds a Docker image from my Dockerfile and pushes it to Docker Hub, tagged so I can pull it later._

_Third stage is **deploy** — it SSHs into my EC2 server, pulls the new image from Docker Hub, stops whatever old container is running, and starts a new one with the updated code._

_So the whole flow is: I push code to GitHub → tests run automatically → if they pass, a Docker image gets built and pushed → then it gets deployed to my server automatically. I never manually build or deploy anything myself once this is set up."_
