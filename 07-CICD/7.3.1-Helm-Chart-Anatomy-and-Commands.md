# Helm — Chart Anatomy, Templating & Commands (GitOps Lab)

## Theory (short)

Helm solves two problems at once: **templating** (write one set of Kubernetes manifests, parameterize the parts that change between environments) and **release management** (Helm tracks what it deployed, so you can `upgrade`, `rollback`, or `history` a release the same way you'd manage a software package — hence "Helm charts," package-manager terminology on purpose).

## Chart anatomy — the mnemonic: "CVT" (Chart, Values, Templates)

```
my-chart/
├── Chart.yaml         # C — identity/metadata for the chart itself
├── values.yaml        # V — the default parameters every template reads from
├── charts/            # subchart dependencies (usually empty unless you declare deps)
├── .helmignore         # like .gitignore, but for what NOT to package
└── templates/          # T — the actual Kubernetes manifests, with {{ }} placeholders
```

**`Chart.yaml`** — answers "what is this chart, what version is it, what version of the app does it deploy." Two version numbers that are easy to confuse:

- `version:` — the **chart's own** version (bump when templates/structure change)
- `appVersion:` — just a label for which version of your actual app this chart currently targets (informational only, doesn't drive templating logic)

**`values.yaml`** — the parameters. Anything a template references via `{{ .Values.x }}` must exist here (or be passed via `--set` at install time, which overrides the file).

**`templates/`** — plain Kubernetes YAML, except values are substituted in via Go templating syntax before being sent to the cluster.

## Creating a chart

```bash
helm create my-chart
```

**Why start here instead of hand-writing files:** `helm create` scaffolds a full, working chart with sensible defaults (Deployment, Service, ServiceAccount, HPA template, ingress template, `_helpers.tpl` for consistent naming) — editing a real scaffold is safer and faster than assembling one from scratch, and less likely to have subtle structural mistakes.

## Writing manifests — templating syntax you'll actually use

```yaml
metadata:
  name: {{ .Values.appName }}
  namespace: {{ .Values.namespace }}
spec:
  replicas: {{ .Values.replicaCount }}
  containers:
    - image: {{ .Values.image.repository }}:{{ .Values.image.tag }}
```

- **`{{ .Values.x }}`** — pulls from `values.yaml`
- **`{{ .Release.Name }}`** — the name given at `helm install <name> .` — useful for naming resources uniquely per release
- **`| quote`** — wraps a value in quotes (needed for values that must be strings in the rendered YAML, e.g. `{{ .Values.port | quote }}`)
- **`| b64enc`** — base64-encodes a value — the only correct way to populate a `Secret`'s `data:` field from a template
- **`{{ required "error message" .Values.x }}`** — **enforces** that a value must be non-empty, or the install/upgrade fails immediately with your custom message, instead of silently deploying with an empty/wrong value

## The `required` function — a real lesson worth internalizing

```yaml
data:
  MONGO_URI: {{ required "secret.mongoUri must be set via --set" .Values.secret.mongoUri | b64enc | quote }}
```

**Why this matters:** a `values.yaml` default of `""` for a required credential silently deploys a broken app if someone forgets to override it. `required` turns that into a loud, immediate failure at install time — the correct behavior for anything the app genuinely cannot function without.

## Real lesson: secrets probably shouldn't be in the chart at all

Even with `required`, values passed via `--set` or `helm.parameters` in an ArgoCD `Application` are **not treated as sensitive** — visible in `helm get values`, `helm history`, shell history, and (if ever committed) permanent Git history. **The more correct pattern for real secrets:** create the `Secret` object manually, once, directly against the cluster — outside Helm entirely — and let your Deployment's `secretKeyRef` find it by name. The chart manages everything _except_ the one thing that's genuinely sensitive.

## Namespace — two separate concepts, easy to conflate

- **`namespace:` in `values.yaml`**, referenced via `{{ .Values.namespace }}` in each template's `metadata.namespace` — controls where the _individual Kubernetes objects_ land
- **`-n <namespace> --create-namespace`** on the `helm install`/`upgrade` command itself — controls where Helm tracks the _release_ (its own bookkeeping, separate from where resources actually deploy)

**Real bug this causes if missed:** resources land in the right namespace, but `helm list` in that same namespace shows nothing — because the release itself got tracked in `default` (wherever your kubectl context defaults to) instead.

## Command reference, with why

```bash
helm template my-chart .              # renders locally, touches nothing — validate before deploying
helm install my-release . -n ns --create-namespace   # first deploy
helm upgrade my-release . -n ns       # apply changes to an existing release
helm rollback my-release 1 -n ns      # revert to a specific prior revision
helm history my-release -n ns         # see every past revision
helm uninstall my-release -n ns       # tear down everything the release created
```
