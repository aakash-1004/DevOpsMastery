# ArgoCD — Application Manifest, Commands & Interview Answers

## Theory (short)

ArgoCD is a **controller that runs inside your cluster**, continuously comparing what's declared in a Git repo against what's actually running, and reconciling any difference. This is fundamentally different from an imperative pipeline (like Jenkins running `kubectl apply` as a build step) — ArgoCD **pulls** from Git on its own schedule; nothing ever **pushes into** the cluster from outside.

**Key fact, proven hands-on twice now (`go-web-app` and `fullstack-chart`):** ArgoCD's reconciliation runs independently of any client viewing it — closing your browser, losing your port-forward, or even your laptop being off entirely has zero effect on whether ArgoCD keeps syncing. The UI is just a window into a process that runs on its own.

## The Application manifest — full field-by-field breakdown

### The mnemonic: **"PSD-S"** — Project, Source, Destination, SyncPolicy

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: fullstack-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/aakash-1004/fullstack-chart.git
    targetRevision: main
    path: .
  destination:
    server: https://kubernetes.default.svc
    namespace: fullstack-app
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

### `metadata.namespace: argocd`

**This is not the namespace your app deploys to.** This `Application` _object itself_ is ArgoCD's own internal bookkeeping — it always lives in the `argocd` namespace (wherever ArgoCD itself was installed), regardless of where the actual app ends up. Two completely separate namespace concepts in the same file — easy to confuse with `destination.namespace` below.

### `spec.project: default`

ArgoCD supports **Projects** — a grouping/permission boundary above individual Applications (which repos are allowed, which clusters, which resource types). `default` is the built-in, unrestricted project that exists automatically. For a personal/lab setup, you'll almost always use `default`; real multi-team companies create separate Projects to scope what each team's Applications are allowed to touch.

### `spec.source` — where the desired state comes from

- **`repoURL`** — the Git repo ArgoCD watches. Must be reachable (public repo, or private with credentials configured separately in ArgoCD).
- **`targetRevision`** — which branch, tag, or commit to track. `main` means "always follow the tip of main" — every new commit becomes the new desired state automatically.
- **`path`** — where _inside_ the repo the chart/manifests live. `.` means the repo root. If your chart were in a subfolder (`helm/fullstack-chart/`), this would need to point there instead.

**Real mistake avoided this session — do NOT do this:**

```yaml
    helm:
      parameters:
        - name: secret.mongoUri
          value: "mongodb+srv://..."
```

This embeds a real secret directly in the `Application` object — visible via `kubectl get application -o yaml`, in ArgoCD's UI, and permanently in Git history the moment this file is committed. The correct `source` block for a chart with externally-managed secrets has **no `helm:` block at all** — ArgoCD just renders the chart using `values.yaml`'s own (non-sensitive) defaults.

### `spec.destination` — where the desired state gets applied

- **`server: https://kubernetes.default.svc`** — this is a **magic, fixed constant**, not a real external URL you look up. It specifically means "deploy to this same cluster ArgoCD itself is running in." (ArgoCD _can_ manage separate, remote clusters too — that uses a different, real API server URL, registered separately — but same-cluster deployment, the vast majority of use cases, always uses this exact string.)
- **`namespace`** — where the actual application resources (Deployments, Services, etc.) land. **This is the value that matters for `kubectl get pods -n <this>`** — completely separate from `metadata.namespace` above, which is just about the `Application` object's own bookkeeping location.

### `spec.syncPolicy` — what makes this GitOps instead of just a dashboard

- **`automated:`** — without this block at all, ArgoCD would only sync when you manually click "Sync" in the UI (still valid GitOps, just manual-trigger). Adding it makes reconciliation fully automatic.
    - **`prune: true`** — if a resource is **removed** from Git, ArgoCD deletes it from the cluster too. Without this, deleting something from your manifests would leave the old resource running forever, orphaned.
    - **`selfHeal: true`** — if someone manually changes something in the cluster directly (`kubectl edit`, `kubectl scale`), ArgoCD reverts it back to match Git. **This is the specific behavior proven live** by manually scaling a Deployment to 5 replicas and watching it revert to the Git-declared count.
- **`syncOptions: - CreateNamespace=true`** — if the target namespace doesn't exist yet, ArgoCD creates it automatically as part of the sync, rather than failing because the namespace is missing.

## Commands — applying and inspecting an Application

```bash
kubectl apply -f argocd-app.yaml
```

**Why a plain `kubectl apply`, not a special ArgoCD-specific command:** the `Application` is just a Custom Resource (a CRD ArgoCD registers) — creating one is identical to creating any other Kubernetes object. ArgoCD's own controller (already running, watching for these objects) picks it up automatically.

```bash
kubectl get application fullstack-app -n argocd
```

Shows `SYNC STATUS` (Synced/OutOfSync) and `HEALTH STATUS` (Healthy/Degraded/Progressing) at a glance — the fastest way to check state without opening the UI at all.

```bash
kubectl port-forward --address 0.0.0.0 svc/argocd-server -n argocd 4400:443
```

**Why `--address 0.0.0.0`:** without it, the forward only binds to the VM's own loopback interface, invisible to a browser on a different machine (like your Windows host reaching into a VirtualBox VM).

```bash
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
```

Retrieves the auto-generated admin password — only valid until you change it for the first time; after that, this command returns the _original_ password, not your current one.

## Cross-cutting lesson: Helm and ArgoCD's secret-handling philosophies actually agree

Both systems arrive at the same real answer independently: **neither Helm's `required` function nor ArgoCD's `Application` manifest are appropriate places to store a real secret value.** The correct pattern in both cases is the same — provision the `Secret` object directly against the cluster, once, outside the templated/GitOps-managed layer entirely, and let `secretKeyRef` in your Deployment find it by name. GitOps manages everything that's safe to declare in Git; secrets are the deliberate, documented exception.

_"I built a full GitOps pipeline for a fullstack app — Express frontend, Flask backend, MongoDB Atlas — packaged as a Helm chart and deployed via ArgoCD. Instead of anyone running `kubectl apply` manually, ArgoCD watches my GitHub repo continuously and keeps the cluster automatically in sync with whatever's declared there. The part I actually spent the most time getting right was secrets — I deliberately kept the database credential completely outside this GitOps loop, provisioning it once directly against the cluster, so it never touches Git, Helm's release history, or the ArgoCD dashboard in plaintext."_

### Why lead with the secrets decision specifically

Same reasoning as your Boardgame quality-gate story — a specific, defensible technical decision is more compelling than a tool list. Anyone can say "I used Helm and ArgoCD." Fewer people can explain _why_ they deliberately excluded one resource from their own automation and back it up with a real reason.

### The deeper, STAR-shaped version

**Situation/Task:** _"I wanted to properly understand the GitOps pattern end to end — not just connect ArgoCD to a repo, but actually build a chart and Application manifest myself, and get the secrets handling right, since that's where I'd seen real mistakes in earlier projects."_

**Action** (in order):

1. _"Built the Helm chart — templated Deployments and Services for both the frontend and backend, a ConfigMap for non-sensitive config like the database name, all parameterized through `values.yaml`."_
2. _"Deliberately did NOT put the MongoDB connection string anywhere in the chart. I created that Secret once, manually, directly in the cluster with `kubectl create secret` — it's never in Git, never in a Helm value, never in the ArgoCD Application manifest."_
3. _"Wrote the ArgoCD Application manifest myself — pointing it at my GitHub repo, telling it which cluster and namespace to deploy into, and enabling automated sync with self-healing turned on."_
4. _"Applied it with one `kubectl apply` — and everything else happened automatically. ArgoCD read the chart, rendered it, and created every resource on its own. I never manually ran `kubectl apply` on the actual application manifests at all."_
5. _"Proved self-healing by manually scaling one of the Deployments to 5 replicas outside of Git — ArgoCD detected that as drift and reverted it back to the Git-declared count within a couple of minutes, with zero action from me."_

**Result:** _"A fully working GitOps loop — push a change to Git, and the cluster updates itself, with the one deliberate exception being the database credential, which stays outside the automation entirely by design."_

### The one-liner they'll remember, if they ask "what's the interesting part"

_"The interesting part wasn't getting ArgoCD to sync — that's mostly configuration. The interesting part was realizing that 'is this value in a Kubernetes Secret' and 'is this value actually protected everywhere it travels' are two different questions, and designing the pipeline so the one genuinely sensitive piece never enters the GitOps loop at all._

## Interview-Ready Spoken Answers

**Q: What is GitOps and how is it different from traditional CI/CD?**

> "GitOps is a deployment model where Git is the single source of truth. In traditional CI/CD like GitHub Actions, the pipeline pushes changes to the cluster — the pipeline needs cluster credentials. In GitOps, an agent like ArgoCD runs inside the cluster and pulls from Git. The cluster reaches out to Git, not the other way around. This means no cluster credentials in the pipeline, full audit trail in Git history, and automatic drift detection."

**Q: What is drift and how does ArgoCD handle it?**

> "Drift is when the live cluster state doesn't match what's defined in Git — for example someone runs kubectl scale manually. ArgoCD continuously compares the live state to the Git state. With selfHeal enabled, it automatically reverts any manual changes back to what Git says. This ensures the cluster always reflects the desired state defined in Git."

**Q: What is the difference between Synced and Healthy in ArgoCD?**

> "Synced means the cluster state matches Git — no drift. Healthy means all the resources are actually running correctly — pods up, no crashes. You want both green. You could be Synced but Degraded if the config in Git deploys correctly but the app itself is crashing. Or OutOfSync but Healthy if someone manually added extra resources to the cluster."

**Q: How do you roll back a deployment with ArgoCD?**

> "Since Git is the source of truth, rollback is just a git revert. You revert the commit that introduced the bad change, push it, and ArgoCD automatically syncs the cluster back to the previous state. You can also use the ArgoCD UI to sync to a specific Git commit directly."

**Q: What is the App of Apps pattern?**

> "It's an ArgoCD pattern for managing large numbers of applications. You create one root Application that points to a directory of other Application manifests in Git. When ArgoCD syncs the root app, it creates all the child Applications, which then each sync their own services. It's how you bootstrap an entire cluster from a single Git repo."

**Q: How do you make ArgoCD sync faster than the default 3 minute poll?**

> "You set up a webhook in GitHub that notifies ArgoCD instantly on every push. The webhook sends a POST request to the ArgoCD API server endpoint. This requires ArgoCD to be publicly accessible — in production on EKS or GKE that's straightforward since the cluster has a public endpoint. For local development you'd use ngrok to create a tunnel."
