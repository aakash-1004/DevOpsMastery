# Jenkins — Controller/Agent Architecture

<!-- nav -->
↑ [[CICD-MOC|CI/CD]] · ← [[7.4-Jenkins-CICD-Pipeline|Jenkins CI/CD — Automated Deployment Pipeline]] · → [[7.4.2-Jenkins-Declarative-Pipeline-Anatomy|Jenkins — Declarative Pipeline Anatomy]]
<!-- /nav -->

## Theory

Jenkins splits into two roles:

- **Controller** — schedules builds, stores config/credentials, serves the UI. Should execute zero builds in production.
- **Agent** — a separate machine that actually runs `sh` steps. Has N **executors** = N concurrent builds. Each build claims one executor and gets a **workspace** directory on the agent's disk.

Routing happens by **label**: `agent { label 'aws-linux' }` sends the build to any online agent carrying that label — not to a hardcoded hostname.

**JS7 parallel (for framing spoken answers):** JOC Cockpit + JS7 Controller orchestrate ≈ Jenkins controller. JS7 Agents execute jobs on target hosts ≈ Jenkins agents. Same split, different product.

**SSH vs JNLP agents:** SSH when the controller can reach the agent (controller dials out). JNLP/inbound when the agent is behind NAT and must dial home to the controller instead.

## Lab — commands, with why

### EC2 agent prep

```bash
java -version
# confirms Java 21 present — Jenkins agent process (remoting.jar) needs a JRE to run at all

sudo useradd -m -s /bin/bash jenkins
# dedicated non-root account — builds should never run as ec2-user/ubuntu or root

sudo mkdir -p /home/jenkins/agent
# this exact path becomes the "Remote root directory" in the node config —
# every build's workspace is created as a subfolder here

sudo chown -R jenkins:jenkins /home/jenkins
# jenkins must own its own home tree or the agent process can't write workspace files

sudo usermod -aG docker jenkins
# only root + docker group members can talk to /var/run/docker.sock —
# skip this and every `docker build` step fails with "permission denied" on the socket

df -h /
free -h
# check disk/RAM headroom before a build dies mid-run with "no space" or gets silently OOM-killed
```

### Controller — generate the SSH key (on bumblebee)

```bash
sudo -u jenkins ssh-keygen -t ed25519 -f /var/lib/jenkins/.ssh/ec2_agent -N ""
# -f puts the key inside jenkins's own .ssh dir — the agent connection runs AS jenkins,
# so the key must live where that account can read it.
# -N "" = no passphrase — Jenkins loads this non-interactively, no human to type one in

sudo cat /var/lib/jenkins/.ssh/ec2_agent.pub
# copy this PUBLIC line only — never the private key file — to paste into the agent
```

### Agent — trust the key

```bash
sudo mkdir -p /home/jenkins/.ssh
sudo tee /home/jenkins/.ssh/authorized_keys > /dev/null <<'EOF'
<paste the ssh-ed25519 ... line>
EOF
sudo chmod 700 /home/jenkins/.ssh
sudo chmod 600 /home/jenkins/.ssh/authorized_keys
sudo chown -R jenkins:jenkins /home/jenkins/.ssh
# sshd's StrictModes silently REFUSES pubkey auth if any of this chain is wrong —
# wrong owner or too-open permissions = single most common "still asks for a password" cause
```

### Controller — pin host key, then test the real chain

```bash
sudo -u jenkins bash -c 'ssh-keyscan -H 3.111.158.123 >> /var/lib/jenkins/.ssh/known_hosts'
# NOTE: sudo -u jenkins ssh-keyscan ... >> file (without bash -c) FAILS —
# the >> redirect is set up by the invoking (non-jenkins) shell before sudo ever runs.
# wrapping the whole thing in `bash -c '...'` is the general fix for sudo + redirect

sudo -u jenkins ssh -i /var/lib/jenkins/.ssh/ec2_agent jenkins@3.111.158.123 'hostname -I; java -version'
# proves the EXACT chain Jenkins will use internally — same user, same key, same host —
# before touching the UI, where errors are far less readable
```

### Jenkins UI

1. Credentials → System → Global → Add: kind **SSH Username with private key**, ID `ec2-agent-key`, username `jenkins`, paste private key contents, **set a Description** (bare username-only labels become ambiguous once a second SSH credential exists)
2. Nodes → New Node → Permanent Agent → configure as in Topology table above
3. Nodes → Built-In Node → Configure → **# of executors: 0**

## Real-world context

Three reasons production Jenkins never builds on the controller:

1. **Security** — a build on the controller runs as the account owning `JENKINS_HOME`, so it can read `credentials.xml` and `secrets/master.key` — decrypting every stored credential. One hostile `Jenkinsfile` compromises the whole CI system.
2. **Resource contention** — a heavy build pegs CPU, the UI stalls, the scheduler stalls.
3. **Disk** — workspaces + Docker layer cache fill `JENKINS_HOME`, which can corrupt job configs.

At scale, static agents don't cut it either — the **Kubernetes plugin** spins up an ephemeral pod per build, runs stages in containers, deletes on completion. Naming this unprompted signals you've thought past a single-box setup.

## Interview-ready spoken answers

**Q: Walk me through Jenkins architecture.**

> Controller holds config, credentials, plugins, job definitions, and the build queue. Agents provide executors. Builds route by label, not hostname. Controller runs zero executors in production — that's a credential-isolation decision, not a default. Agents connect either outbound-from-controller via SSH, or inbound via JNLP when the agent's behind NAT and has to dial home.

**Q: Your pipeline — where did the builds actually run?**

> [Honest-bridge framing, not invented]: Started as a single-VM setup where builds ran on the built-in node. I've since separated it — dedicated EC2 agent, SSH key scoped to a locked-down service account, controller set to zero executors, label-based routing. [State the risk you understood and the fix — this reads as senior. Claiming a 5-agent fleet you never built does not, because the follow-up question exposes it.]

**Q: Why zero executors on the controller?**

> A build running there executes as the account owning `JENKINS_HOME` — it can decrypt every stored credential. Isolating execution to an agent contains that blast radius to just that box.

**Q: SSH agent vs JNLP agent — when would you use each?**

> SSH when the controller can reach the agent. JNLP/inbound when the agent's on a private network or ephemeral and must dial home instead.

**Q: What was the hardest part of setting this up?** _(good STAR-adjacent real answer)_

> `sudo command >> restricted-file` fails silently because the shell sets up that redirect before sudo elevates — only the command itself runs as the target user, not the redirect. Fix is wrapping the whole thing in `sudo -u user bash -c '...'`. Small thing, but it's the difference between having followed a tutorial and having actually built it.
