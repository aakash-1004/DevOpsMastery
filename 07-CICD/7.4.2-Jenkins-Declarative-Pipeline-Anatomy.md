# Jenkins — Declarative Pipeline Anatomy

<!-- nav -->
↑ [[CICD-MOC|CI/CD]] · ← [[7.4.1-Jenkins-Controller-Agent-Architecture|Jenkins — Controller/Agent Architecture]] · → [[Lab-Taskmanager-CICD|Lab — CI/CD Pipeline for Taskmanager]]
<!-- /nav -->

## Theory

**Declarative vs scripted:** Declarative is a structured, validated DSL (`pipeline { agent {} stages {} post {} }`) — readable, checked before it runs. Scripted is raw Groovy — more power, harder to review. Default to declarative always. Your real 13-stage pipeline is already declarative — correct choice, not a limitation.

**Top-level directives, typical order:**

|Directive|Purpose|
|---|---|
|`agent`|Where it runs — `none`, `any`, or `{ label '...' }`|
|`options`|Pipeline-wide behavior — timeouts, timestamps, concurrency|
|`parameters`|Human-supplied inputs at trigger time|
|`environment`|Variables available to every stage|
|`stages`|The actual work, as named `stage` blocks|
|`post`|Runs after all stages — `always`/`success`/`failure`/`unstable`|

**Rule confirmed by hitting it directly:** a stage that contains `parallel` (or `matrix`) **cannot** also declare its own top-level `agent` — the `agent` has to live on each parallel branch instead, since different branches may need different agents. Declarative validates this at parse time, before any step runs.

## Lab — practice repo

Repo: `github.com/aakash-1004/jenkins-pipeline-practice` (kept separate from real project repos — this is a structural exercise, not portfolio work).

```groovy
pipeline {
    agent none
    // forces every stage to declare its own agent — explicit per-stage placement,
    // the pattern real multi-stage pipelines use

    options {
        timestamps()
        timeout(time: 15, unit: 'MINUTES')
        disableConcurrentBuilds()
    }

    parameters {
        booleanParam(name: 'DEPLOY', defaultValue: false, description: 'Run the deploy stage?')
    }

    environment {
        APP_NAME = 'jenkins-block2-demo'
    }

    stages {
        stage('Checkout') {
            agent { label 'aws-linux' }
            steps { sh 'echo "Checking out on $(hostname -I)"' }
        }

        stage('Build') {
            agent { label 'aws-linux' }
            steps { sh 'echo "Building ${APP_NAME} build #${BUILD_NUMBER}"' }
        }

        stage('Test') {
            parallel {
                // agent lives on EACH branch here, not on the parent "Test" stage —
                // this is the rule the compiler enforced (see below)
                stage('Unit Tests') {
                    agent { label 'aws-linux' }
                    steps { sh 'echo "running unit tests"; sleep 5' }
                }
                stage('Integration Tests') {
                    agent { label 'aws-linux' }
                    steps { sh 'echo "running integration tests"; sleep 5' }
                }
            }
        }

        stage('Deploy') {
            agent { label 'aws-linux' }
            when { expression { params.DEPLOY == true } }
            steps { sh 'echo "Deploying ${APP_NAME}..."' }
        }
    }

    post {
        always  { echo 'Pipeline finished — runs regardless of outcome' }
        success { echo 'Build succeeded' }
        failure { echo 'Build failed — Slack/email alert hook goes here' }
        unstable { echo 'Build unstable — tests failed but build succeeded' }
    }
}
```

Job config: **Pipeline script from SCM** (not pasted inline) — every real pipeline lives in the repo it builds, with diff history and PR review.

**Verified both branches of `when`:** `DEPLOY=false` → `Stage "Deploy" skipped due to when conditional`. `DEPLOY=true` → Deploy stage executes. Both confirmed in console output.

## The debugging saga (the actual learning, not the happy path)

### 1. Git checkout failing — looked like credentials, wasn't

Public repo, Jenkins still prompted for credentials. Root cause chain, each one ruled out in order:

- Repo visibility (confirmed Public on GitHub)
- Network/DNS from bumblebee (`sudo -u jenkins git ls-remote <url>` returned clean commit hashes)
- The inline UI validator itself — it's a separate AJAX check using the Jenkins **process's** environment, fires once, doesn't auto-retry, and can show a stale/wrong error even when the real checkout path works fine. **Lesson: trust Console Output over the inline red-text validator — they run through different code paths.**

### 2. Real failure: JVM couldn't spawn ANY subprocess (not git-specific, not network)

```
java.io.IOException: Failed to exec spawn helper: pid: 900237, exit code: 1, error: 0 (none)
Caused: ... Cannot run program "git" ... Failed to exec spawn helper
```

**Read root-cause-first:** Jenkins stack traces list the deepest cause at the _top_, each subsequent block is higher-level code re-wrapping it — opposite of typical Java traces where you scroll to the bottom.

**Actual cause:** Ubuntu 24.04+ defaults `kernel.apparmor_restrict_unprivileged_userns = 1`. The JDK's native `jspawnhelper` binary (used by `ProcessBuilder.start()` to fork external processes) relies on unprivileged user-namespace creation — AppArmor blocks it, surfacing as this exact cryptic, content-free error.

**Confirmed via:**

```bash
lsb_release -a                                          # Ubuntu 24.04.2 LTS
sysctl kernel.apparmor_restrict_unprivileged_userns      # = 1, confirms restriction active
```

**Fix — scoped to the Jenkins JVM only**, via the actual systemd drop-in (not the legacy `/etc/default/jenkins`, which this install doesn't use):

```bash
sudo nano /etc/systemd/system/jenkins.service.d/override.conf
```

```ini
[Service]
Environment="JENKINS_PORT=8090"
Environment="JAVA_OPTS=-Djava.awt.headless=true -Djdk.lang.Process.launchMechanism=VFORK"
```

**Critical gotcha:** systemd doesn't append to a repeated `Environment=` key — a later declaration fully **replaces** the earlier one. Had to re-include `-Djava.awt.headless=true` alongside the new flag, or it would've been silently dropped.

```bash
sudo systemctl daemon-reload
sudo systemctl restart jenkins
```

Verified the flag actually reached the running JVM (not just the config file):

```bash
ps aux | grep '[j]ava' | grep -o 'launchMechanism=[A-Z]*'   # → launchMechanism=VFORK
```

`VFORK` makes the JVM spawn subprocesses via `vfork()` instead of the `jspawnhelper`/clone() path AppArmor blocks — sidesteps the restriction, doesn't weaken it system-wide. **This fix is now permanently applied on bumblebee — don't redo it.**

### 3. `agent` + `parallel` compile error

```
"agent" is not allowed in stage "Test" as it contains parallel or matrix stages
```

Covered in Theory above — fixed by moving `agent` from the parent `Test` stage down onto each parallel branch.

## Real-world gotchas found in the SUCCESSFUL build's own log

**Parallel syntax ≠ actual concurrency.** Timestamps showed Unit Tests and Integration Tests running back-to-back (~15s total for two 5s branches), not overlapping (~6-7s expected). Cause: `ec2-agent` node still has the Jenkins default of **1 executor** — both branches request the same label and queue behind each other on the single executor, despite correct `parallel` syntax. **Fix (not yet applied):** Nodes → `ec2-agent` → Configure → executors: 2.

**Every stage that declares its own `agent` re-clones the whole repo.** Counted 5 separate `checkout`/git-clone blocks in one pipeline run — one per stage acquiring a fresh agent, because Declarative can't assume a later stage lands on the same machine as an earlier one. Cheap on a 3-line demo repo; a real cost on a large repo. **Standard fix (not yet applied, later block):** `stash`/`unstash` — checkout once, stash the files, unstash in later stages instead of re-fetching from GitHub.

## Interview-ready spoken answers

**Q: Walk me through a Jenkinsfile's structure.**

> `pipeline` block, `agent` decides where it runs — top-level or per-stage — `options` sets pipeline-wide behavior like timeouts, `stages` holds the work as named blocks, `post` handles what happens after, keyed on success/failure/always. Declarative over scripted for readability and validation.

**Q: Declarative vs scripted?**

> Declarative is a structured, validated DSL — standard for new pipelines. Scripted is raw Groovy, more powerful, harder to maintain. I've built everything in declarative; I understand scripted exists but haven't needed its flexibility.

**Q: How would you speed up a slow CI/CD pipeline?**

> Identify independent stages — unit tests, integration tests, security scans rarely depend on each other — and run them with `parallel`. Highest-leverage, lowest-risk optimization before touching infrastructure. [Good follow-up if pushed]: parallel syntax alone isn't enough — the agent needs enough executors for branches to actually run concurrently, otherwise they queue behind each other on a single executor despite correct syntax. I hit this directly building a test pipeline.

**Q: Describe a tricky production-adjacent issue you debugged.** _(strong real STAR-adjacent answer)_

> A pipeline failed with what looked like a Git authentication error — public repo, no credentials configured, so that didn't add up. Traced it down through the actual stack trace instead of trusting Jenkins's UI-level error: root cause was several layers deeper — the JVM itself couldn't spawn _any_ subprocess, because Ubuntu 24.04's AppArmor policy blocks the JDK's native process-spawning helper by default. Fixed it by setting `-Djdk.lang.Process.launchMechanism=VFORK` in the Jenkins service's systemd override, scoped to just that JVM. The instructive part was reading the exception chain root-cause-first instead of assuming the surface-level Git error was the real one.

**Q: What's the `agent`/`parallel` interaction rule?**

> A stage containing `parallel` can't declare its own top-level agent — placement has to move to each parallel branch, since different branches might need different agents. Declarative enforces this at compile time, before any step runs.
